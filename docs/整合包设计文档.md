# 审计工具整合包设计文档

## 1 设计结论

整合包首版采用“统一启动器加三个隔离子工具”的结构：用户从一个入口选择工具，三个既有工具仍在独立进程中运行，并作为同一个 Windows 发布包交付。该方案能统一入口、版本和发布流程，同时保留各工具已经验证过的业务行为，避免基金测算的工作簿写入、文件序号工具的原地重命名和病历抽取的只读处理互相影响。

本阶段只建立整合项目和设计基线，不复制三个源项目的代码，也不改变其现有行为。实施阶段先导入并锁定源版本，再增加启动器和统一构建，不在首版重写业务算法或合并三套 Tkinter 窗口。

## 2 阅读与验证基线

设计以 2026-09-13 读取到的以下版本为准。

| 组件 | 来源与分支 | 基线版本 | 当前形态 | 验证结果 |
| --- | --- | --- | --- | --- |
| 病历自动抽取工具 | `E:\Auto Extract Medical Record`，`main` | `c10f916`，工具 V1.8 | `app.py` 界面和 `extractor.py` 业务逻辑 | 16 项测试通过；本地与 `origin/main` 同步 |
| 基金金额自动测算工具 | `E:\auto-amount-calc`，`main` | 本地 `8ebd324`，工具 V0.8.1 | 单文件 `fund_calculator.py` | 19 项测试和 7 个子测试通过；本地比 `origin/main` 多 7 个提交 |
| 文件批量添加序号工具 | `git@github.com:ZealotSarah/Auto_add_Number.git`，`develop_1` | `1f0324a` | 单文件 `main.py` | Python 语法检查通过；仓库未提供自动化测试 |

### 2.1 病历自动抽取工具

该工具批量读取 `.xlsx`，识别业务工作表和字段，按检查日期过滤，合并同一病历，在年份间分配名额并优先抽取住院记录。固定随机种子可以复现结果。输出为全新的 Excel，包含“抽取结果”“运行汇总”“异常明细”“参数”四个工作表；源文件保持只读。姓名保留，人员或个人编号、身份证或证件号整列排除。

现有分层较清楚：`app.py` 负责 Tkinter、设置持久化和后台线程，`extractor.py` 负责字段映射、日期解析、病历合并、抽样与结果写入。它适合在整合时保持原模块边界。

### 2.2 基金金额自动测算工具

该工具读取一个或多个 Excel，根据通用、串换或固定比例规则，按医疗机构、险种和医疗类别分组计算基金金额，并写入新增的“基金测算”工作表。成功保存前会生成临时工作簿并重新校验，随后为测算前原文件创建时间戳备份，再替换工作文件；失败时应保持或恢复原文件。

当前界面、业务逻辑和文件安全逻辑集中在 `fund_calculator.py`。整合阶段不能把它的写入流程改成病历工具的“始终新建结果文件”，也不能绕过现有备份、保存后校验和恢复机制。

### 2.3 文件批量添加序号工具

该工具支持批量、单文件和按文档标题三种重命名模式。用户先确认旧文件名到新文件名的预览映射，再执行原地重命名；标题可从 DOCX 或 PDF 元数据及正文提取。批量模式按用户排序执行，被占用的文件会跳过，后续文件继续按预览中的序号处理。

当前业务和界面全部集中在 `main.py` 的 `FileRenameApp` 中。运行时错误可能导致部分文件已重命名且不能自动回滚，所以首版必须把预览、确认和结果汇总原样保留，并在统一入口明确标识其风险等级。

## 3 项目目标与边界

### 3.1 首版目标

1. 提供一个统一的“审计工具箱”启动器，展示三个工具的名称、用途、版本、文件影响和启动按钮。
2. 将三个工具及其依赖打包为一个可复制、可离线运行的 Windows 发布目录或压缩包。
3. 每个子工具独立启动、独立退出；某个工具崩溃不终止启动器或其他工具。
4. 统一记录整合包版本、组件版本和源提交，构建结果可以追溯。
5. 保留三套工具现有输入、输出、隐私、安全和错误处理语义。
6. 建立自动化测试、构建和人工冒烟检查的统一入口。

### 3.2 首版不做

- 不把三个工具的业务参数拼成一个复杂窗口。
- 不把三套任务串成固定工作流；它们没有稳定的前后置数据契约。
- 不新增数据库、Web 服务、用户登录或联网处理。
- 不改变既有 Excel 字段映射、金额计算、抽样或重命名规则。
- 不承诺通用撤销；文件重命名工具仍遵循其当前行为。
- 不直接从三个源仓库的最新分支自动构建，必须使用锁定提交。

## 4 总体架构

```text
用户
  |
  v
审计工具箱启动器  launcher.exe
  |-- 读取 component-lock.json 并显示版本和风险说明
  |-- 启动 medical-record/病历自动抽取工具.exe
  |-- 启动 fund-calculator/基金金额自动测算工具.exe
  `-- 启动 file-renamer/文件批量添加序号工具.exe

三个子工具使用独立进程、独立窗口和独立日志
  |-- 病历抽取：只读源 Excel，写新结果文件
  |-- 基金测算：备份后更新所选 Excel
  `-- 文件序号：预览确认后原地重命名
```

选择进程隔离的理由：

- 三个工具都已有独立 Tkinter 事件循环，直接嵌入同一进程需要大范围改造。
- 第三方依赖和 PyInstaller 隐式导入可以按组件分别控制，降低打包回归风险。
- 文件写入权限、崩溃和长任务线程彼此隔离，故障边界清晰。
- 后续可以单独升级某个工具，而不必同时修改另外两个业务模块。

## 6 源码导入与版本管理

### 6.1 推荐策略

首版采用“单仓库内导入组件源码并记录来源”的方式，不使用 Git submodule。发布构建因此只需克隆一个仓库，不依赖构建机额外取得三个仓库的权限或正确检出嵌套分支。

`component-lock.json` 至少记录：

```json
{
  "medical_record": {
    "repository": "git@github.com:ZealotSarah/Auto-Extract-Medical-Record.git",
    "branch": "main",
    "commit": "c10f9162d22e7bf5cde5b4f27bcb0cbb678b93e9"
  },
  "fund_calculator": {
    "repository": "git@github.com:ZealotSarah/auto-amount-calc.git",
    "branch": "main",
    "commit": "8ebd3243e91cd4a7b2fb7e5920551ce84a924d81"
  },
  "file_renamer": {
    "repository": "git@github.com:ZealotSarah/Auto_add_Number.git",
    "branch": "develop_1",
    "commit": "1f0324ad1a8e9082fcb1c9ca959d608d7115c6c8"
  }
}
```

导入脚本只接受显式提交哈希，导入后运行组件测试并检查工作区差异。同步新版组件时，在单独提交中更新源码和锁文件，便于审查与回退。

### 6.2 实施前必须解决的版本问题

基金工具的设计基线 `8ebd324` 尚未存在于当前 `origin/main`，因为本地分支比远端多 7 个提交。在导入整合包之前，应先将这些提交推送并确认远端可访问，或明确改用远端 `deb9b36`。不应在锁文件中长期记录其他构建机无法取得的提交。

## 7 启动器设计

启动器只负责发现和启动工具，不处理业务文件。主界面包含三个工具卡片，每张卡片显示：

- 工具名和组件版本；
- 一句话用途；
- 支持的主要文件类型；
- 文件影响等级；
- “启动工具”按钮；
- 组件缺失或损坏时的明确错误。

建议的文件影响标签：

| 工具 | 标签 | 固定提示 |
| --- | --- | --- |
| 病历自动抽取 | 只读源文件 | 结果写入新的 Excel；源文件不修改 |
| 基金金额测算 | 修改工作簿并备份 | 成功时新增结果工作表，并保留测算前备份 |
| 文件批量添加序号 | 原地修改文件名 | 必须检查预览；执行后可能部分成功且不能自动回滚 |

启动器通过 `subprocess.Popen` 启动发布目录中的固定相对路径。它不使用 shell 拼接命令，不接受用户输入作为可执行文件路径，并把当前工作目录设置为对应组件目录。重复点击时允许启动多个实例还是聚焦现有实例，应在实施时选择；首版建议禁用同一组件的重复启动，避免同一批文件被并发处理。

## 8 组件隔离与最小改造

### 8.1 病历自动抽取

- 保留 `app.py` 和 `extractor.py` 的现有分层。
- 保留当前 `%APPDATA%\病历自动抽取工具\settings.json` 配置路径，避免升级后丢失用户设置。
- 打包入口继续调用 `app.main()`。
- 不改变源文件哈希不变和隐私列排除规则。

### 8.2 基金金额自动测算

- 首版原样迁入 `fund_calculator.py`，只为打包路径或版本信息做必要适配。
- 保留临时文件校验、时间戳备份、原文件替换和失败恢复顺序。
- 不把它改成统一的“输出目录”模式，因为这会改变已确认的业务流程。
- 组件退出码和错误日志只用于启动器诊断，业务失败仍在组件窗口内展示。

### 8.3 文件批量添加序号

- 首版保留 `FileRenameApp` 和现有三种模式。
- 把窗口创建移动到明确的 `main()` 入口是允许的最小重构，但不能改变预览和执行逻辑。
- 在纳入整合发布前补齐自动化测试，优先覆盖重名冲突、已占用文件、跳过后的序号空缺、非法字符和取消格式。
- 标题提取仍限制为可读取文本的 DOCX 和 PDF，不在首版加入 OCR。

## 9 依赖与运行环境

统一使用项目虚拟环境和锁定依赖。当前可见依赖为：

- `openpyxl==3.1.5`；
- `pyinstaller==6.14.2`；
- `python-docx`；
- `PyPDF2`；
- Windows 下用于隐藏属性识别的可选 `pywin32`；
- Tkinter 和其他 Python 标准库。

开发基线可先采用已验证测试的 Python 3.12.x。构建脚本必须输出实际 Python、PyInstaller 和组件版本。依赖版本在首次整合测试通过后全部固定，不在构建时无约束地升级。

## 10 构建与发布

### 10.1 构建产物

首版建议使用 PyInstaller `onedir`，形成以下发布目录：

```text
审计工具整合包-<bundle-version>/
|-- 审计工具箱.exe
|-- component-lock.json
|-- medical-record/病历自动抽取工具.exe
|-- fund-calculator/基金金额自动测算工具.exe
`-- file-renamer/文件批量添加序号工具.exe
```

不建议首版把全部内容压成一个 `onefile` EXE。多组件 `onefile` 会重复解压运行时、启动较慢，也更难定位杀毒软件误报和第三方库缺失。最终对用户仍只交付一个 ZIP 或安装包。

### 10.2 构建顺序

1. 校验 `component-lock.json` 与导入源码的提交信息。
2. 安装锁定依赖。
3. 分别运行三个组件的单元测试。
4. 运行启动器和发布目录测试。
5. 分别构建三个组件，再构建启动器。
6. 在干净临时目录执行发布版冒烟测试。
7. 生成 SHA-256 校验文件和版本清单。
8. 将完整目录压缩为单个发布包；代码签名在具备证书时作为正式发布步骤执行。

## 11 文件安全与隐私约束

| 风险面 | 设计约束 |
| --- | --- |
| 病历数据 | 全程本地处理；源 Excel 只读；结果不包含人员或个人编号、身份证或证件号列；日志不写敏感值 |
| 基金测算 | 写入前完成参数和字段校验；保存临时副本并复核；保留测算前备份；失败时不得留下看似成功的结果 |
| 文件重命名 | 执行前展示完整映射并检查冲突；明确提示原地修改；逐项记录成功、跳过和失败 |
| 启动器 | 不读取业务文件内容，不上传数据，不收集遥测，不把文件路径发送到网络 |
| 日志 | 默认只记录时间、组件、版本、进程结果和脱敏错误；不记录 Excel 单元格内容、患者标识或文档正文 |

整合包不能用一个模糊的“运行成功”覆盖组件内部的部分失败。每个组件继续负责自己的业务结果；启动器只报告“已启动”“无法启动”和“进程异常退出”。

## 12 测试方案

### 12.1 保留的组件测试

- 病历工具现有 16 项测试必须持续通过。
- 基金工具现有 19 项测试和 7 个子测试必须持续通过，包括保存、备份和脱敏样例回归。
- 文件序号工具在首次发布前新增测试，不能只依赖语法检查。

### 12.2 新增整合测试

| 编号 | 场景 | 验收结果 |
| --- | --- | --- |
| IT-01 | 启动器读取版本清单 | 三个组件名称、版本和风险标签准确显示 |
| IT-02 | 三个组件文件均存在 | 每个启动按钮都能打开对应窗口，启动器保持可用 |
| IT-03 | 某组件 EXE 缺失 | 只禁用该组件并显示具体缺失路径，其他组件仍可启动 |
| IT-04 | 组件异常退出 | 启动器记录组件名、版本和退出码，不包含业务敏感数据 |
| IT-05 | 从含中文和空格的目录运行 | 三个组件均可启动，资源和配置路径解析正确 |
| IT-06 | 发布目录被整体复制 | 不依赖开发机绝对路径，复制后仍能运行 |
| IT-07 | 同一组件重复启动 | 第二次启动按既定策略被阻止或明确提示 |
| IT-08 | 无网络环境 | 启动和三项核心功能不依赖网络 |

### 12.3 人工冒烟测试

1. 病历工具：用脱敏样例抽取，确认源文件哈希不变，四个结果工作表存在。
2. 基金工具：在样例副本上测算，确认备份存在、结果工作表与金额校验通过。
3. 文件序号工具：在临时目录预览并重命名，覆盖成功、占用跳过和名称冲突三种情况。
4. 启动器：逐个启动、关闭和再次启动组件，检查中文路径、版本展示和错误提示。

## 13 实施顺序与完成标准

### 阶段一 锁定组件

- 解决基金工具 7 个未推送提交的来源问题。
- 为文件序号工具补测试。
- 建立组件锁文件并导入三个源码快照。
- 完成标准：每个组件都能从整合仓库独立运行，原测试全部通过。

### 阶段二 统一启动与构建

- 实现启动器、组件注册表和安全的进程启动。
- 建立 PyInstaller 规格和统一构建脚本。
- 完成标准：干净环境从一个发布目录启动三个工具，不依赖源项目路径。

### 阶段三 发布验收

- 运行组件回归、整合测试和人工冒烟测试。
- 生成版本清单、校验值和发布压缩包。
- 完成标准：数据安全约束全部满足，测试结果可追溯，发布包可在 Windows 10/11 离线运行。

## 14 主要风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 基金工具本地提交未推送 | 其他构建机无法重现基线 | 实施前推送或重新选择可访问提交 |
| 文件序号工具无测试且单文件较大 | 重构或打包容易引入回归 | 先补行为测试，再做最小入口调整 |
| 三套工具都使用 Tkinter | 同进程整合事件循环复杂 | 首版使用独立进程 |
| 写入语义不同 | 统一包装可能掩盖数据风险 | 在启动器中显示固定风险标签，组件保留自身确认流程 |
| PyInstaller 隐式依赖和中文路径 | 构建后组件可能启动失败 | 独立 spec、干净目录和中文路径冒烟测试 |
| 组件源码复制导致版本漂移 | 修复未同步或来源不清 | 锁文件、显式导入脚本和单独同步提交 |

## 15 后续演进条件

只有在首版稳定后，才考虑把公共的文件选择、日志、版本展示或 Excel 表头识别提取为共享库。共享代码必须来自至少两个组件已经证明相同的需求，不能只因实现看起来相似就合并。若未来需要跨工具流水线，应先定义输入输出文件契约和失败恢复策略，再增加编排功能。
