# 飞检工具包设计文档

## 1 设计结论

整合包首版采用“单窗口三个标签页加独立业务 Worker”的结构：用户切换标签页即可进入对应工具，三个组件的源码、状态、配置和测试保持独立，耗时或写文件操作在通过 Windows `spawn` 创建的独立进程中执行。该方案统一了操作体验，同时隔离基金测算的工作簿写入、文件序号工具的原地重命名和病历抽取任务。

三个标签页共享一个 Tkinter 主事件循环，但不相互导入业务代码。统一外壳只负责按需加载、进程通信、运行状态和安全关闭；组件 Worker 负责实际业务。首版不重写既有算法，文件重命名工具通过适配层嵌入，待行为测试补齐后再拆分其历史单文件代码。

### 2.1 病历自动抽取工具

该工具批量读取 `.xlsx`，识别业务工作表和字段，按检查日期过滤，合并同一病历，在年份间分配名额并优先抽取住院记录。固定随机种子可以复现结果。输出为全新的 Excel，包含“抽取结果”“运行汇总”“异常明细”“参数”四个工作表；源文件保持只读。姓名保留，人员或个人编号、身份证或证件号整列排除。

现有分层较清楚：`app.py` 负责 Tkinter、设置持久化和后台线程，`extractor.py` 负责字段映射、日期解析、病历合并、抽样与结果写入。它适合在整合时保持原模块边界。

### 2.2 基金金额自动测算工具

该工具读取一个或多个 Excel，根据通用、串换或固定比例规则，按医疗机构、险种和医疗类别分组计算基金金额，并写入新增的“基金测算”工作表。成功保存前会生成临时工作簿并重新校验，随后为测算前原文件创建时间戳备份，再替换工作文件；失败时应保持或恢复原文件。

当前界面、业务逻辑和文件安全逻辑集中在 `fund_calculator.py`。整合阶段不能把它的写入流程改成病历工具的“始终新建结果文件”，也不能绕过现有备份、保存后校验和恢复机制。

### 2.3 文件批量编码工具

该工具支持批量、单文件和按文档标题三种重命名模式。用户先确认旧文件名到新文件名的预览映射，再执行原地重命名；标题可从 DOCX 或 PDF 元数据及正文提取。批量模式按用户排序执行，被占用的文件会跳过，后续文件继续按预览中的序号处理。

当前业务和界面全部集中在 `main.py` 的 `FileRenameApp` 中。运行时错误可能导致部分文件已重命名且不能自动回滚，所以首版必须把预览、确认和结果汇总原样保留，并在统一入口明确标识其风险等级。

## 3 项目目标与边界

### 3.1 首版目标

1. 提供一个统一的“飞检工具包”窗口，以三个标签页直接承载现有工具界面。
2. 将三个工具及其依赖打包为一个可复制、可离线运行的 Windows 发布目录或压缩包。
3. 标签页按需加载；业务任务在独立 Worker 中运行，某个 Worker 异常不关闭主窗口。
4. 统一记录整合包版本、组件版本和源提交，构建结果可以追溯。
5. 保留三套工具现有输入、输出、隐私、安全和错误处理语义。
6. 建立自动化测试、构建和人工冒烟检查的统一入口。

### 3.2 首版不做

- 不把三个工具的业务参数拼成一个复杂窗口。
- 不把三套任务串成固定工作流；它们没有稳定的前后置数据契约。
- 不新增数据库、Web 服务、用户登录或联网处理。
- 不改变既有 Excel 字段映射、金额计算、抽样或重命名规则。
- 不承诺通用撤销；文件重命名工具仍遵循其当前行为。
- 不直接从三个源仓库的最新分支自动构建，必须使用锁定提交。

## 4 总体架构

```text
用户
  |
  v
飞检工具包单窗口  FlightInspectionToolsApp
  `-- ttk.Notebook
      |-- 文件批量编码 Tab -> file_renamer Worker
      |-- 病历抽取 Tab ----> medical_record Worker
      `-- 基金测算 Tab ----> fund_calculator Worker

统一外壳：标签页、按需加载、状态和安全关闭
组件包：独立业务代码、版本、配置和测试
Worker：结构化参数输入、进度或结果输出、安全取消检查点
```

选择“共享界面、隔离业务”的理由：

- 三个工具均为 Tkinter，界面可改造为同一 `ttk.Notebook` 下的 `Frame`。
- 主进程只运行界面事件循环，长任务不会阻塞其他标签页。
- 文件写入、异常和取消边界由各组件 Worker 控制。
- 组件之间禁止直接导入，可独立测试和更新源码快照。

## 6 源码导入与版本管理

### 6.1 推荐策略

首版采用“单仓库内导入组件源码并记录来源”的方式，不使用 Git submodule。发布构建因此只需克隆一个仓库，不依赖构建机额外取得三个仓库的权限或正确检出嵌套分支。

`component-lock.json` 至少记录：

```json
{
  "medical_record": {
    "repository": "git@github.com:ZealotSarah/Auto-Extract-Medical-Record.git",
    "branch": "main",
    "commit": "c10f9162d22e7bf5cde5b4f27bcb0cbb678b93e9"
  },
  "fund_calculator": {
    "repository": "git@github.com:ZealotSarah/auto-amount-calc.git",
    "branch": "main",
    "commit": "8ebd3243e91cd4a7b2fb7e5920551ce84a924d81"
  },
  "file_renamer": {
    "repository": "git@github.com:ZealotSarah/Auto_add_Number.git",
    "branch": "develop_1",
    "commit": "1f0324ad1a8e9082fcb1c9ca959d608d7115c6c8"
  }
}
```

导入脚本只接受显式提交哈希，导入后运行组件测试并检查工作区差异。同步新版组件时，在单独提交中更新源码和锁文件，便于审查与回退。

### 6.2 已确认版本状态

三个锁定提交均已存在于对应 GitHub 远端，可以在其他构建机重现。同步新版组件时仍必须先确认目标提交可通过远端取得。

## 7 标签页外壳设计

主窗口创建 `ttk.Notebook` 和三个轻量占位页，顺序固定为“文件批量编码、病历自动抽取、基金金额测算”。用户第一次选择标签页时才导入并创建对应界面。某个组件初始化失败时，仅把该页替换为错误页，其他标签页继续可用。外壳显示工具包版本和当前标签页的文件影响说明。

窗口根据当前屏幕宽高计算初始尺寸并居中显示，不写死单一分辨率；同时启用水平和垂直缩放，用户可拖动窗口边框自行调节。Notebook、标签页容器、文件列表和日志区使用 `fill` 与 `expand` 消化尺寸变化，输入控件保持必要的最小可用尺寸。

建议的文件影响标签：

| 工具 | 标签 | 固定提示 |
| --- | --- | --- |
| 病历自动抽取 | 只读源文件 | 结果写入新的 Excel；源文件不修改 |
| 基金金额测算 | 修改工作簿并备份 | 成功时新增结果工作表，并保留测算前备份 |
| 文件批量编码 | 原地修改文件名 | 必须检查预览；执行后可能部分成功且不能自动回滚 |

每个标签页只构造参数和展示结果，通过 `ProcessTaskRunner` 启动一个 `spawn` Worker。主进程用队列接收结构化进度、结果和脱敏错误，不能把 Tkinter 对象、打开的工作簿或文件句柄传给 Worker。同一标签页同一时间只允许一个任务；关闭主窗口时只要有 Worker 运行，就阻止退出。

## 8 组件隔离与最小改造

### 8.1 病历自动抽取

- 保留 `app.py` 和 `extractor.py` 的现有分层。
- 保留当前 `%APPDATA%\病历自动抽取工具\settings.json` 配置路径，避免升级后丢失用户设置。
- 界面改为 `MedicalRecordTab(ttk.Frame)`，业务调用进入独立 Worker。
- 不改变源文件哈希不变和隐私列排除规则。

### 8.2 基金金额自动测算

- 首版原样迁入 `fund_calculator.py`，只为打包路径或版本信息做必要适配。
- 保留临时文件校验、时间戳备份、原文件替换和失败恢复顺序。
- 不把它改成统一的“输出目录”模式，因为这会改变已确认的业务流程。
- 界面改为 `FundCalculatorTab(ttk.Frame)`；每个文件之间检查取消请求，单文件内部仍由原安全保存流程控制。

### 8.3 文件批量编码

- 首版通过 `EmbeddedHost` 和子类适配器保留 `FileRenameApp` 的三种模式与预览逻辑。
- 实际 `os.rename` 计划交给独立 Worker；Worker 在每个文件之间检查取消请求并逐项返回成功、跳过和失败。
- 在纳入整合发布前补齐自动化测试，优先覆盖重名冲突、已占用文件、跳过后的序号空缺、非法字符和取消格式。
- 标题提取仍限制为可读取文本的 DOCX 和 PDF，不在首版加入 OCR。

## 9 依赖与运行环境

统一使用项目虚拟环境和锁定依赖。当前可见依赖为：

- `openpyxl==3.1.5`；
- `pyinstaller==6.14.2`；
- `python-docx`；
- `PyPDF2`；
- Windows 下用于隐藏属性识别的可选 `pywin32`；
- Tkinter 和其他 Python 标准库。

开发基线可先采用已验证测试的 Python 3.12.x。构建脚本必须输出实际 Python、PyInstaller 和组件版本。依赖版本在首次整合测试通过后全部固定，不在构建时无约束地升级。

## 10 构建与发布

### 10.1 构建产物

首版建议使用 PyInstaller `onedir`，形成以下发布目录：

```text
飞检工具包-<bundle-version>/
|-- 飞检工具包.exe
|-- component-lock.json
`-- _internal/
    |-- audit_tools_bundle/
    `-- components/
```

首版使用 PyInstaller `onedir`。主程序与 Worker 来自同一个构建产物，`multiprocessing.freeze_support()` 负责 Windows 打包后的子进程入口。暂不使用 `onefile`，避免每次创建 Worker 都重复解压运行时。

### 10.2 构建顺序

1. 校验 `component-lock.json` 与导入源码的提交信息。
2. 安装锁定依赖。
3. 分别运行三个组件的单元测试。
4. 运行标签页、Worker 和发布目录测试。
5. 构建统一主程序并验证 Worker 子进程。
6. 在干净临时目录执行发布版冒烟测试。
7. 生成 SHA-256 校验文件和版本清单。
8. 将完整目录压缩为单个发布包；代码签名在具备证书时作为正式发布步骤执行。

### 10.3 Windows 安装程序

使用 Inno Setup 6 把 `onedir` 发布目录封装为安装程序。安装范围默认为当前 Windows 用户，目标目录为 `%LOCALAPPDATA%\Programs\飞检工具包`，不申请管理员权限。安装程序创建开始菜单入口和卸载入口，桌面快捷方式由用户选择；相同 `AppId` 的后续版本执行原位升级。

安装程序必须经过一次临时目录静默安装测试：确认主程序和 `_internal` 完整落盘，运行发布版 Worker 冒烟，启动 GUI，最后通过生成的卸载程序清理测试安装。

## 11 文件安全与隐私约束

| 风险面 | 设计约束 |
| --- | --- |
| 病历数据 | 全程本地处理；源 Excel 只读；结果不包含人员或个人编号、身份证或证件号列；日志不写敏感值 |
| 基金测算 | 写入前完成参数和字段校验；保存临时副本并复核；保留测算前备份；失败时不得留下看似成功的结果 |
| 文件重命名 | 执行前展示完整映射并检查冲突；明确提示原地修改；逐项记录成功、跳过和失败 |
| 统一外壳 | 不读取业务文件内容，不上传数据，不收集遥测；只把用户已选择的路径交给对应 Worker |
| 日志 | 默认只记录时间、组件、版本、进程结果和脱敏错误；不记录 Excel 单元格内容、患者标识或文档正文 |

整合包不能用一个模糊的“运行成功”覆盖组件内部的部分失败。各标签页继续展示组件级结果；统一外壳只负责初始化错误、运行状态和 Worker 异常退出。

## 12 测试方案

### 12.1 保留的组件测试

- 病历工具现有 16 项测试必须持续通过。
- 基金工具现有 19 项测试和 7 个子测试必须持续通过，包括保存、备份和脱敏样例回归。
- 文件序号工具在首次发布前新增测试，不能只依赖语法检查。

### 12.2 新增整合测试

| 编号 | 场景 | 验收结果 |
| --- | --- | --- |
| IT-01 | 外壳读取版本清单 | 三个标签名称、组件版本和风险说明准确显示 |
| IT-02 | 依次选择三个标签页 | 每个页面按需初始化，切换后状态保持 |
| IT-03 | 某组件导入失败 | 仅对应标签显示错误，其他标签仍可使用 |
| IT-04 | Worker 异常退出 | 对应标签显示退出信息，不关闭主窗口且不输出敏感数据 |
| IT-05 | 从含中文和空格的目录运行 | 三个标签页及 Worker 均能解析资源和用户路径 |
| IT-06 | 发布目录被整体复制 | 不依赖开发机绝对路径，复制后仍能运行 |
| IT-07 | 同一标签重复启动任务 | 第二次启动被阻止并保持原任务状态 |
| IT-08 | 无网络环境 | 启动和三项核心功能不依赖网络 |

### 12.3 人工冒烟测试

1. 病历工具：用脱敏样例抽取，确认源文件哈希不变，四个结果工作表存在。
2. 基金工具：在样例副本上测算，确认备份存在、结果工作表与金额校验通过。
3. 文件序号工具：在临时目录预览并重命名，覆盖成功、占用跳过和名称冲突三种情况。
4. 统一外壳：逐个切换标签页，检查状态保持、中文路径、Worker 失败和安全关闭提示。

## 13 实施顺序与完成标准

### 阶段一 锁定组件

- 为文件序号工具补测试。
- 建立组件锁文件并导入三个源码快照。
- 完成标准：每个组件都能从整合仓库独立运行，原测试全部通过。

### 阶段二 统一启动与构建

- 实现标签页外壳、组件注册表和 Worker 进程运行器。
- 建立 PyInstaller 规格和统一构建脚本。
- 完成标准：干净环境从一个窗口使用三个标签页，所有写文件任务不依赖源项目路径。

### 阶段三 发布验收

- 运行组件回归、整合测试和人工冒烟测试。
- 生成版本清单、校验值和发布压缩包。
- 完成标准：数据安全约束全部满足，测试结果可追溯，发布包可在 Windows 10/11 离线运行。

## 14 主要风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 文件序号工具无测试且单文件较大 | 重构或打包容易引入回归 | 先补行为测试，再做最小入口调整 |
| 三个标签页共享 Tkinter 主进程 | UI 回调异常可能影响整个窗口 | 按需加载并在组件边界捕获异常；业务放入 Worker |
| 写入语义不同 | 统一包装可能掩盖数据风险 | 在标签页显示固定风险提示，组件保留自身确认流程 |
| PyInstaller 隐式依赖和中文路径 | 构建后组件可能启动失败 | 独立 spec、干净目录和中文路径冒烟测试 |
| 组件源码复制导致版本漂移 | 修复未同步或来源不清 | 锁文件、显式导入脚本和单独同步提交 |

## 15 后续演进条件

只有在首版稳定后，才考虑把公共的文件选择、日志、版本展示或 Excel 表头识别提取为共享库。共享代码必须来自至少两个组件已经证明相同的需求，不能只因实现看起来相似就合并。若未来需要跨工具流水线，应先定义输入输出文件契约和失败恢复策略，再增加编排功能。
